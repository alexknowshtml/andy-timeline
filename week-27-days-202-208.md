### The Mistakes We Made

#### 1. The Fork Exhaustion Crisis

**Cost:** EAGAIN errors and `ERR_WORKER_INIT_FAILED` propagated across services despite healthy file descriptors. Multiple services failed simultaneously without an obvious shared cause.\
**Fix:** `812a0af04`, `bc0f74849`, `bf9b24e17`, `a68f96a20` — Batched `ps`/`cgroup`/`podman` calls in `generate-port-registry`; switched `/proc` reads from `execSync` to `readFileSync`; wrote spawn audit SOP + cron inventory; wired `audit-spawn-footprint` into `/diagnose-bridge` Step 7\
**Lesson Learned:** When `EAGAIN` shows up alongside healthy FDs, look at fork rate, not resource leak. High-frequency cron scripts that spawn per-item subprocesses are the canonical cause. Batch external commands; read `/proc` files directly.

#### 2. The Reaction Sync Cascade

**Cost:** Three sequential bugs in the Discord reaction sync — over-fetching null-reaction messages, infinite loop on skipped messages, buffer overflow on large reaction sets. Each fix exposed the next.\
**Fix:** `2f0ed368b`, `9e6ff58c3`, `c7352f485`, `45524cf58` — Excluded null-reaction messages, fixed loop counter advancement, paginated batching (twice — second commit was the actual fix)\
**Lesson Learned:** Sync pipelines hide error cascades because each broken stage prevents the next stage from receiving data. Validate input boundaries at every stage so failures surface independently, not in a chain.

#### 3. The Mawn OpenTable Sniper Retirement

**Cost:** A week of iteration — v1 (Patchright + Akamai bypass), v2 (browser-harness + Dia CDP), GQL API switch, dual-strategy booking, monthly release window prep, test booking mode — then full removal. Sunk cost in maintenance complexity for a goal that didn't justify it.\
**Fix:** `4dfd0dc8d` — Remove Mawn OpenTable sniper (all versions)\
**Lesson Learned:** Set a "this isn't worth maintaining" threshold up front. The sniper crossed it the day it required Akamai-bypass infrastructure plus monthly release window timing logic. Removal was the right move, but earlier removal would have been better.

#### 4. The Byline Retirement Took Three Passes

**Cost:** "Remove byline — retired experiment" → "Remove last byline traces — scrub complete" → "Remove final byline cache files generated during retirement". Three commits to fully kill an experiment because the cache files kept regenerating.\
**Fix:** Each pass killed a different layer (code, cache, post-retirement regeneration)\
**Lesson Learned:** Experiments need an explicit retirement spec from day one — what writes data, what reads it, what schedules it. Otherwise the cleanup is a bisection problem.

#### 5. The 8-Day Silent Relationship Refresh Outage

**Cost:** Relationship refresh stopped working April 19–20 when `~/.gmail-mcp/credentials.json` refresh token expired. Gmail MCP had been retired but `scan-sent-emails.ts` still pointed at its dead OAuth flow. 240 sent emails to 67 recipients piled up unprocessed before the gap was noticed today.\
**Fix:** `f6664fab0`, `91b4d8051`, `9b8db262c` — Refactored scanner to `gog-wrapper.sh` (Andy Core's working credentials), bumped `max-results` 50→300, ran the backfill (13 new + 50 updated person files)\
**Lesson Learned:** When you retire a system (Gmail MCP), grep for every consumer first. Dead-credential breakage is silent — the script doesn't fail loudly, the data just stops flowing.

### The Surprising Things

#### 1. The /context-xray Skill Changed Optimization Priorities Overnight

**Expected:** The live context window visualizer would be a debugging tool for one-off questions\
**Actual:** Per-block cost attribution showed where tokens were *actually* going. Some blocks assumed expensive were cheap; others assumed cheap were expensive. Within two days, optimization priorities shifted across MEMORY.md, CLAUDE.md, and the includes layer.

The compounding lesson: **measurement preceded prioritization**. Until you could see per-block cost, every optimization was a guess.

#### 2. The Decisive Opus Review Pass Cleared 100 Hung Items in One Batch

**Expected:** 100 `needs_review` email templates would take multiple Opus runs and curated context\
**Actual:** A single `--review` pass with a binary-decision prompt that forbade hedging cleared all 100. The bottleneck was never Opus capacity — it was that the original prompt allowed "defer" as an output, which the model used liberally.

This reusable pattern got memorized: when a queue hangs in `needs_review`, the prompt is the bug.

#### 3. The Email Template Pipeline Reached Production in Two Days

**Expected:** Phase 0 prototype (Day 204) would lead to weeks of iteration before producing usable templates\
**Actual:** Day 206 added template matching to drafts. Day 207 shipped Phase 1-3 unified pipeline + DB state tracking + review UI + `/pending-email-templates` command. Day 208 processed 200+ templates in production with a polished review UI (pill filters, keyboard shortcuts, search autocomplete).

The compounding factor: every prior pipeline pattern (DB-backed queue, two-pass agents, decisive review pass) was already in the system. The email template pipeline didn't invent the orchestration — it composed it.

#### 4. graph:decay Had Been Defined But Never Scheduled

**Expected:** The rolling memory graph's decay curve had been quietly running since Phase 3 shipped on Day 202\
**Actual:** `graph:decay` was defined in Laravel's `console.php` but no Bree job ever fired it. Six days of "decay" work that never happened. Same pattern as relationship-warming-detector (Day 198): code exists, schedule doesn't. Fixed by adding `graph-decay.cjs` and registering it at 2am ET daily.

The compounding lesson: console-defined commands without scheduler entries are dead code. The fix needs to be structural — ideally a registration check that warns when `console.php` defines a job that's not in `scheduler.cjs`.
