## Day 192: One-Time Job Infrastructure & Flight Check-In (April 11, 2026)

### The One-Time Job System

**Commits `33f7ff30d`, `34a9d5595`, `63c27b7c7`, `80faa9dc8`, `c9ce43f8e`**

An entire scheduling subsystem was built in a single day, driven by a concrete need: automated flight check-ins. Bree's native date-based one-time jobs live only in memory — a scheduler restart before the job fires silently loses it.

The solution came in three layers:

1. **bree-plugin-one-time** (`33f7ff30d`) — A Bree plugin that persists one-time jobs to disk. Jobs survive scheduler restarts. A v1.0.1 fix (`80faa9dc8`) caught an infinite recursion in the `start()` wrapper.

2. **internal scheduling API** (`63c27b7c7`) — An endpoint on an internal API port that lets any process schedule a one-time job on the running scheduler. Without this, jobs could only be added at startup.

3. **discord-ping worker** (`34a9d5595`) — A test worker wired in alongside the plugin to prove the system worked end-to-end before building the real use case.

### /flight-checkin: Opus-Guided Browser Automation

**Commits `189038da3`, `6f5486fa4`, `517cc12b9`, `8bb1bac46`**

The `/flight-checkin` skill went through three architectures in one day:

1. **v1: Playwright script** (`6f5486fa4`) — Hardcoded navigation steps on Mac Mini: enter confirmation code, enter last name, screenshot every step.
2. **v2: Agentic browser loop** (`517cc12b9`, `8bb1bac46`) — Reworked to an Opus-guided loop. Instead of hardcoded navigation, Opus observes each page state via screenshot and decides the next action. This handles the unpredictable page variations that airlines throw at automated check-ins.
3. **Disposable worker pattern** (`9522bc2a2`) — One-time workers that self-archive after execution, keeping the scheduler clean.

The skill SSHs to the Mac Mini, runs Playwright, pulls screenshots back, reports to Discord, and saves a paper trail. All scheduled via the new one-time job system.

**Lesson Learned:** Building infrastructure for a single use case (flight check-in) is justified when the infrastructure is genuinely reusable. The one-time job system now powers any "do X at time Y" pattern — flight check-ins are just the first consumer.

## Reflection: Week 25

---

### The Mistakes We Made

#### 1. Opus 4.6 Premature Deployment

**Cost:** Opus 4.6 was deployed as the default model, but something in its behavior didn't match expectations. A revert to 4.5 was needed, requiring commits across multiple files before centralization was complete.\
**Fix:** `4c1e65dc6` - Revert, then `8e4eec804` - Centralize all model strings into config/claude.php so future version changes are a single env var\
**Lesson Learned:** Model upgrades should be staged (one service at a time with observation) rather than deployed globally. Centralized config makes rollbacks trivial.

#### 2. bree-plugin-one-time Infinite Recursion

**Cost:** The v1.0.0 release had an infinite recursion bug in the `start()` wrapper — discovered only when the scheduler actually tried to start.\
**Fix:** `80faa9dc8` - v1.0.1 fixed the wrapper\
**Lesson Learned:** Bree plugins that wrap lifecycle methods need careful testing of the wrap-and-call pattern. A recursive `start()` that calls itself instead of the original is an easy mistake to make.

#### 3. Event Reminders Send Test Hitting CSRF

**Cost:** The send test button was failing with 419 errors because the endpoint was behind CSRF protection that the AJAX call wasn't satisfying.\
**Fix:** `2fb26b2b7` - Exempt from CSRF, rely on session auth instead\
**Lesson Learned:** Internal API endpoints called by authenticated admin UIs don't need CSRF protection — session auth is sufficient and avoids the token dance.

### The Surprising Things

#### 1. A Three-Architecture Flight Check-In in One Day

**Expected:** Building automated flight check-in would be a multi-day project requiring careful Playwright scripting\
**Actual:** Three complete architectures (hardcoded Playwright → Opus-guided agentic loop → disposable worker pattern) shipped in a single day, plus the entire one-time job infrastructure underneath them

The Opus-guided browser loop was the breakthrough — instead of scripting every click path, you give Opus a screenshot and ask "what should I do next?" Airlines constantly change their check-in flows, so a vision-guided approach is more durable than hardcoded selectors.

#### 2. Andy's Identity Layer Changed Session Quality

**Expected:** SOUL/MEMORY/DREAMS would be reference documents read occasionally\
**Actual:** Sessions after the identity layer was added showed more consistent judgment on ambiguous decisions — Andy had a clearer sense of its own values and priorities to draw from when the right answer wasn't obvious

#### 3. /upskill Creates a Compounding Loop

**Expected:** Skill maintenance would continue to be manual\
**Actual:** /upskill turned session learnings into automatic skill updates. Skills improved between sessions without human intervention — the lift-philly, model-delegation, and andy-core-dev skills all got better through automated extraction.
