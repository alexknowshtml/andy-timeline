## Day 351: P3 Edit Idempotency Resolved, Luma Sync Marathon, and Amy Hoy's Curriculum Session (September 17, 2026)

### P3 Edit Idempotency: The Root Fix

**Commits `fcecbaf38a` (P3 tri-state), `2db77990ee` (embed tri-state + unconfirmed tracking)**

The Discord service's edit reliability problem finally got its root fix. The original bug: `editDiscordMessage` and `editDiscordEmbed` both returned `boolean`, with a 5-second timeout. A timed-out edit returned `false` — and callers treated that as "not sent," immediately re-posting the same content as a new message or re-sending the same embed on every poll tick.

`fcecbaf38a` promotes `editDiscordMessage` to `'ok' | 'failed' | 'unknown'` — timeout/abort maps to `'unknown'`, not failure. The edit timeout was bumped from 5s to 20s. On `'unknown'`, the state is preserved with no retry (retrying while unknown causes the 40s stall under 429). `closeSegment` reconciles at segment end using `confirmedMessageText` rather than the unconfirmed current text, preventing double-counting.

`2db77990ee` applies the same promotion to `editDiscordEmbed`. The `subagent-watcher` gains `unconfirmedEmbedKey/unconfirmedAt/editFailures/frozen` tracking — it skips re-send while outcome is unknown, force-confirms at `stop()` for the final blue→green transition, and freezes the panel after `MAX_EDIT_FAILURES` consecutive definitive rejections.

## Day 353: GH #764 Untangled — Prompt Architecture Split and the Fable Fork Guard Gains a Briefing Checklist (September 19, 2026)

### GH #764: Move [ANDY-INTERNAL-TASK] to appendSystemPrompt

**Commits `e9ff618dea` (fix), `6e9e793018` (followup), `7cb042395b` (revert of wrong fix)**

The `[ANDY-INTERNAL-TASK]` framing tag had been traveling in the `-p` argument alongside Alex's words. Claude Code wraps `-p` content in `<pasted_content>` tags — and the untrusted-content safety rule fired on that wrapper, blocking legitimate go-ahead approvals for commits and pushes. The symptom: Alex would approve a commit in Discord, and Andy would refuse to act because the approval text was being treated as untrusted external content.

The fix split `buildPrompt()` into two functions: `buildPrompt()` now carries only Alex's actual words, reply context, and attachments. `buildContextBlock()` carries the framing, agent context, and instructions — delivered via `appendSystemPrompt`. An earlier attempt (`d77ec183e4`) declared `pasted_content` trusted in `appendSystemPrompt`, which solved the symptom but wrong-routed the context. That was reverted (`7cb042395b`). The right fix is structural: framing never belongs in the user turn.

### Fable Fork Guard: Parent Model Detection and Briefing Checklist

**Commits `9a3dc10d4c` (parent model from transcript), `77491bd9e7` (args-first), `7c869a6a0d` (briefing checklist), `efa6399d52` (reason per item)**

The fable-fork-guard hook received four improvements: it now reads the parent model from the Claude process args first (more reliable than transcript lookup), exits via `exit 2` to properly block via stderr, and — most usefully — the denial text now carries a full briefing checklist with a reason for each item. When Alex forks to Fable, the guard tells the session exactly what it should brief the fork on and why, instead of a bare "blocked" message.

### sweep-claude-state.sh and Session-Recovery Completion Fix

**Commit `d90cde234e` (sweep script), `41a354a876` (recovery completion)**

`sweep-claude-state.sh` landed as a standalone script for cleaning orphaned hook state files — JSON and log files that accumulate in `.claude/state/` when sessions crash or exit unexpectedly. A companion fix (`41a354a876`) corrected the context-exhaustion recovery path: it was marking recovery complete before the session had actually resumed, producing cases where the recovery "succeeded" but the thread stayed stuck.

**Lesson Learned:** Prompt architecture has a trust boundary: framing and instructions belong in `appendSystemPrompt` (trusted); user words belong in `-p` (untrusted by design). Mixing them produces safety-rule collisions that look like bugs in the safety system but are actually configuration errors.

### discord-completion and discord-thread-job Fixes

**Commits `b8e4c374fc` (stale snapshot), `114af8c32a` (busy flag), `6a5ed0fba8` (claudeSessionId), `218215d36a` (reset on exhaustion), `0f51971a2c` (PRIORITY on new session only), `ab0e1ebb2c` (dead code deleted)**

`b8e4c374fc` is the week's most architecturally significant fix: when a dead session is reset, `initial_context` was left pointing at the first-turn snapshot. On threads where the snapshot said "Not answered" (10% of live threads), `ProcessDiscordThreadMessage` was injecting a `PRIORITY` directive that caused the fresh session to re-run a request from the thread's first turn — a ghost task from session zero.

`resetDeadSession()` and `retry()`'s dead-session guard now write a neutral stub that names the dead transcript instead. The stub has no `## Last Request from Alex` heading, so the `PRIORITY` check cannot fire. The `PRIORITY` directive itself was also gated to new sessions only (`0f51971a2c`). Dead proactive-recovery methods were deleted entirely (`ab0e1ebb2c`, 89 lines).

The handoff page sessions list was reversed — most recent at top — with the latest session badged. Long thread histories are now collapsible. Several layout fixes landed alongside (word-break, meta row wrapping, flexbox overflow).

### claude-state-hygiene: Weekly Cleanup Job

**Commits `2d1692720b` (weekly job), `9f7f2b0e8f` (retention rules), `6b99b9a01a` (180-day context-pin retention)**

A weekly `claude-state-hygiene` job landed, running Sundays at 4:40am ET. It deletes stale hook state files, rotates the `context-warning.log`, and applies tiered retention: context-pin files are kept 180 days (up from 30), handoff-announced files follow their own retention. **Lesson Learned:** A 10% ghost-task rate (28 of 283 live threads) is a silent correctness problem that looks like "Andy is weirdly re-doing old work." Separating the recovery stub from the original snapshot — and gating PRIORITY on session newness — closes the entire class. The fix required understanding three interacting systems: initial_context snapshots, the PRIORITY directive, and the dead-session reset path.

## Reflection: Week 48

---

### The Mistakes We Made

#### 1. GH #764: Framing and User Words Traveled Together in -p

**Cost:** Alex's go-ahead approvals (commit, push, send) were being blocked by the untrusted-content safety rule because `[ANDY-INTERNAL-TASK]` framing was in the same `-p` block as Alex's words, and Claude Code wraps `-p` content in `<pasted_content>`. A first fix attempt (`d77ec183e4`) declared `pasted_content` trusted — solving the symptom but wrong-routing the architectural fix — and had to be reverted.\
**Fix:** `e9ff618dea` split `buildPrompt()` into two paths: framing to `appendSystemPrompt`, user words to `-p` only.\
**Lesson Learned:** Prompt delivery channels carry implicit trust levels. Mixing framing with user input in the same delivery channel makes the trust boundary ambiguous. The split should be structural from the start.

#### 2. editDiscordEmbed Returned boolean — Re-Send Loop Until Session Ended

**Cost:** The `subagent-watcher` treated a timed-out embed edit as "not sent" and re-sent the same embed payload on every poll tick — a busy re-send loop that ran until the session ended. The same root cause (boolean return from edit functions) caused the P3 duplicate-post bug in `editDiscordMessage`.\
**Fix:** `2db77990ee` promoted `editDiscordEmbed` to `EditResult` tri-state with unconfirmed tracking, mirroring the fix applied to `editDiscordMessage` in `fcecbaf38a`.\
**Lesson Learned:** Both edit functions shared the same boolean return type and 5s timeout. Once the root cause was identified in one, the other should have been fixed simultaneously. Fixing half a symmetric bug invites the other half to surface.
