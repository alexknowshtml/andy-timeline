## Overview: A Redesign, a New Skill Family & a Recurring Cleanup

Week 28 was defined by three big builds that each replaced something fragile with something durable. The **Google Meet processing pipeline** was rebuilt end-to-end after a May 1 failure — the old single-pass job was reading a 106KB transcript into session context, then writing a 111KB meeting file back, blowing out context before side effects could run. The replacement is a multi-pass pipeline with a thread per meeting, a watchdog that retries stalled sessions, and a dual-button review gate for reminder creation. The **/research skill** landed alongside a new `samma-esana` web search discipline — distilled evidence hierarchy and degradation grammar from a Zenodo paper, wired into `/fact-check`, `/file-this`, and `/sales-safari` so every web fetch downstream inherits the discipline. The **garage-rain-alert** scheduled job was born on Day 211 and matured across Day 211–212 in 13+ commits — Tomorrow.io polling, ClickSend SMS escalation, format-change detection, lookahead tightening (60min → 10min), TypeScript rewrite with .cjs shim. The week also closed last week's open thread: **scanner failure alerting** shipped on Day 209 to catch silent `invalid_grant` errors so the next 8-day Gmail outage surfaces the same hour. The `/reflect` command got three structural fixes (Sessions API for subagent discovery, no auto-implementation, Discord heartbeat posts). The `lift-philly` skill was refactored from 226 lines to 101 with intent routing and 3 new includes. `write-post` absorbed `authentic-post` as a voice-first interview/extract mode. A new `markdown-to-gdoc` skill formalized the find-replace silent-failure gotcha. The Mazzoni Center HIV Testing Event agreement was prepared and sent for signature.

**Key themes:** Google Meet multi-pass pipeline, `/research` skill + samma-esana discipline, garage-rain-alert born & matured, `/reflect` stabilized, `lift-philly` refactor, write-post + authentic-post merger, scanner failure alerting (closing last week's gap), Discord async session lifecycle SOP, sticky note extraction pipeline, AI Hero funnel strategy.

## Day 213: Google Meet Pipeline Redesign (May 2, 2026)

### Multi-Pass Pipeline + Thread + Review Gate

**Commit `37a27d04a`**

The defining commit of the week. Root cause of the May 1 Google Meet processing failure: a 106KB transcript was read into session context and then written back as a 111KB meeting file — blowing out context before side effects (reminders, Discord posts) could run.

The redesign:
- **`ProcessGoogleMeetTranscript`** now delegates to a multi-pass pipeline (never embeds transcript in session); adds `threadId`/`docId` constructor fields; tracks state JSON (`status`, `processingStartedAt`, `sessionId`) at spawn time; passes `incrementalPosting` to `spawnClaude()` for streaming thread updates.
- **`ProcessGoogleMeetReminders`** (new): lightweight job that parses Alex's action items from the meeting file and creates reminders; idempotent via `remindersCreated` flag; posts count confirmation to Discord thread.
- **`bot.ts`**: `handleGmeetProcessButton` now creates a workbench thread off the embed before dispatching, turns embed gold, passes `threadId` to API; new `handleGmeetApproveRemindersButton` routes ✅ Create Reminders taps.
- **`DiscordWebhookController`**: `gmeetProcess` accepts `threadId`; new `gmeetApproveReminders` and `gmeetRetry` endpoints.
- **`poll-google-meet-transcripts.cjs`**: `runWatchdog()` added — detects sessions with `status=processing` and `processingStartedAt > 15min`; retries up to 2x then marks failed; posts status to Discord thread.
- **Removed 500-line size check** — always multi-pass now.

### The Mistakes We Made

#### 1. The Google Meet Context Blowout

**Cost:** A 106KB transcript was read into session context, then written back as a 111KB meeting file — context exhausted before reminders could be created or Discord could be notified. Side effects of the meeting processing job silently dropped.\
**Fix:** `37a27d04a` — Multi-pass pipeline (never embed transcript in session), state JSON tracking at spawn time, watchdog with 15min stall detection + retry, separate `ProcessGoogleMeetReminders` job for the side-effect tail, dual review-gate buttons (✅ Create Reminders / 📋 Post without reminders).\
**Lesson Learned:** When a job both reads large input and writes large output in the same session, the fix is structural — split into passes, stage side-effects through a queue, and watchdog the long-runners. Prompt engineering can't save you from architecture mistakes.

#### 2. The Discord Button-Click Silence (600 Seconds)

**Cost:** A `suggest-option` button click sent to Andy Core without `incrementalPosting` produced a Claude session with no streaming — complete Discord silence for 600s in incident session 7ffdc91f. The forensic dive also found `DISCORD_ANNOUNCE_DEFAULT_MODEL` firing on every async wrapper, not just fresh @mentions, producing spurious model indicators on thread continuations.\
**Fix:** `4e808e20b` (silence + model indicator), `0777bee13` (audit script + SOPs + JSDoc/PHPDoc) — `injectSmartButton` now passes `incrementalPosting`; model indicator gated to `ProcessDiscordMention` only via `$isMention` param; payload audit script verifies all 5 async call sites have required fields; lifecycle SOP + offline runbook documented.\
**Lesson Learned:** Async chain bugs surface as silence, not errors. A single 600s incident produced two new SOPs, a payload audit script, JSDoc on the affected functions, and code fixes for two bugs. Wiring the lessons back into checks is the only way they survive.

#### 3. The 8-Day Silent Outage Almost Repeated

**Cost:** Last week's relationship-refresh outage went 8 days unnoticed because `scanner-stats.json` reported `status=error` and nothing alerted on it. Without explicit alerting, the same `invalid_grant` failure would silently recur the next time a credential expired.\
**Fix:** `5cd97c18d` — Two-layer alerting: (1) `relationship-refresh.cjs` throws when `scanner-stats.json` reports error status (uses existing Discord mention notification path), (2) `scan-sent-emails.ts` directly POSTs a Discord ping with @mention when the scanner errors (belt-and-suspenders, framework-independent).\
**Lesson Learned:** A retrospective without enforcement is just a story. The 8-day outage produced a code fix (gog-wrapper + max-results bump) on Day 208 — but the *enforcement* fix (alert on error status) didn't ship until Day 209. Both are necessary; only one is durable.

#### 4. The garage-rain-alert v1 Was the Spike, Not the Ship

**Cost:** First version of `garage-rain-alert` shipped at 8:15pm on Day 211 with a 60-minute rain lookahead, no SMS, no format-change detection, no early-exit, no persistent state, no snapshot tests. None of these were obvious gaps until the job ran in production.\
**Fix:** Days 211-212 produced 13+ commits hardening the job — TypeScript rewrite, snapshot tests, ClickSend SMS, 10-minute lookahead (the 60min was producing alerts for rain that wouldn't arrive in time to matter), format-change detection, dedup, persistent state, 6am–midnight restriction.\
**Lesson Learned:** Treat scheduled-job v1 as the spike. The harden pass — adding snapshot tests, format guards, persistent state, escalation paths — is the actual ship. Schedule the harden pass into the same calendar block as the build.

#### 5. The Documenso Y-Offset Round Trip

**Cost:** A -5% Y offset had been added to Documenso field positions on 2026-04-17 to fix what looked like a positioning bug. The offset was then reverted on Day 211 after testing showed the offset itself broke field positions for other agreements. The original Y coords (Indy Hall 29.46%, Partner 42.85%) were the correct ones.\
**Fix:** `c220f8a7f` — Revert -5% Y offset, restore baseline coordinates.\
**Lesson Learned:** Layout fixes for one document can break others. Memory entry [Documenso field positions](feedback_documenso_field_position_shift.md) was already updated noting the revert; the round trip itself is the lesson — global offsets fix one case at the cost of N others.

### The Surprising Things

#### 1. Two New Skills Born From an Imported Paper

**Expected:** Web search discipline improvements would come from internal use patterns and trial-and-error\
**Actual:** A Zenodo paper (MIT License) on `samma-esana` search discipline — evidence hierarchy, 10-phase loop, stopping conditions, degradation grammar — was distilled into an include + a `/research` skill in a single Day 211 commit, then immediately wired into 3 existing skills (`/fact-check`, `/file-this`, `/sales-safari`).

External methodology arrived as 174 inserted lines and made 3 existing skills measurably more disciplined overnight. The compounding lesson: not all improvements come from inside the system; sometimes the right paper finds you.

#### 2. The lift-philly Skill Got Smaller as It Got More Capable

**Expected:** Adding council PDF, citation standard, maintenance docs, i18n handoff workflow would grow the skill file\
**Actual:** SKILL.md went from 226 lines to 101 lines. The capability count went up; the line count went down. The pattern that made this work: extract verbatim sections to includes, replace inline content with intent routing.

The takeaway: skill files should be thin routers, not encyclopedias. The encyclopedia goes in the includes.

#### 3. The Google Meet Failure Produced a New Pipeline Pattern

**Expected:** The May 1 failure would be patched with a context-size guard or a chunked variant of the existing job\
**Actual:** The fix was a full architectural redesign — multi-pass pipeline with state tracking, separate jobs for processing vs side-effects, a watchdog for stalled sessions, dual review-gate buttons, threadId-aware embed updates. 10 files changed, 765 insertions.

The Google Meet redesign joins the email template pipeline (Days 207-208) and the LIFT Philly petition moderation pipeline (Days 203-205) as the third "pipeline pattern" landed in the past three weeks. The reusable pattern crystallizing: **input-stage → state-tracked job → review-gate buttons → side-effect job**, with a watchdog for stalls.

#### 4. The garage-rain-alert Found Format-Change Detection Useful Within Hours

**Expected:** A scheduled job that reads from a Discord channel would have to assume the channel format is stable\
**Actual:** Day 211 evening commits added warnings for "bot messages exist but none match regex" and Discord alerts for format change. By Day 212 morning, the format-change detection was hardened with dedup. Treating the source format as adversarial — likely to drift — produced a more robust job than treating the format as stable.

The compounding lesson: any sync that depends on parsing third-party output (Discord bot messages, email headers, scraped HTML) should have format-drift alerts from day one. The cost is small; the silent-failure cost when format changes is high.
