## Day 342: jfdibot Goes Approval-First (September 8, 2026)

### The Autonomous Posting Path Is Removed

**Commit `7cd19cb215`**

Forty-eight hours after shipping the autonomous Twitter posting agent, the auto-posting path was removed entirely. The refactored `jfdibot-post.cjs` now takes only the approval-first path: gather content → invoke Claude for a draft → write a pending state file → create a Discord approval thread. There is no `autoPost` branch anymore, no confidence gate that triggers silent posting.

The reason: jfdibot shipped with a workbench-thread approval flow as the primary path for borderline cases, but the 80% confidence threshold gave the system an autonomous exit that bypassed the thread entirely. That path had never been confirmed end-to-end — the daily rate limit was hit on Day 340 before the first confident post went through. Removing the autonomous path first — then re-earning it after a longer test period — is the right order.

### Tailscale HTTPS Block

**Commit `548ebfcf9a`**

A guard was added at two layers to prevent `tailscale serve --https=443` from accidentally exposing internal services over the public tailnet HTTPS certificate. The block operates at the script level (env check) and at the Caddy layer (return 403 on tailscale-proxied requests to restricted routes). Tailscale's serve feature makes it easy to accidentally make a service public; the guard makes "no" the default.

**Lesson Learned:** Shipping a feature that bypasses manual review and then reversing the bypass two days later is not failure — it's the correct feedback loop. The right time to remove the autonomous path is before the first production mistake, not after.

## Day 343: Hooks Get Smarter — Subagent Continuation Loop (September 9, 2026)

### Subagent Chain, Injector, and Detector

**Commits `d9d923c04d` (chain + injector + detector), `4c00077ad2` (imsg photos)**

A three-piece system for auto-chaining subagents that hit context limits shipped: `lib/subagent-chain.ts` provides shared utilities (chain ID, step tracking, partial result extraction, next-prompt scaffolding); a `subagent-budget-injector` hook automatically injects remaining budget into every Agent call before it starts; a `subagent-continuation-detector` hook intercepts the stop event when a subagent exhausts its budget and enqueues the next chain step.

The problem it solves: a long subagent task (relationship sync, bookmark processing, research) would hit context limits and silently stop — the orchestrator had no way to know whether the result was partial or complete. The chain gives subagents a structured way to hand off remaining work to the next step without the orchestrator needing to detect the failure.

### iCloud Photos Endpoints on imsg-server

The imsg-server (Mac Mini) gained `/photos/export` (iCloud download via osxphotos `--download-missing`), `/photos/screenshots` with smart-album type filtering, and a raised idle timeout. Newer screenshots on the Mini are iCloud-only placeholders — `/photos/file` returns 404 because the file has never been downloaded locally. The export endpoint pulls them on demand.

### Newsletter and AI Hero Cohort 05

The September 7 newsletter was broadcast (#25840854). The AI Hero Cohort 05 Software Factory Strategy session ran the same day — notes drafted, replay processed, Q4 Software Factory project directory created with Amy's engagement estimate.

**Lesson Learned:** The subagent continuation loop inverts the failure model: instead of "work until you can't, then stop," it's "work until you can't, then hand off cleanly." The partial result and remaining work are preserved as first-class outputs, not lost.

## Day 344: Video Bookmark Pipeline Gets an Escalation Ladder (September 10, 2026)

### Download Escalation + Frame Extraction

**Commits `1d62bda79b` (escalation), `125cb8c72e` (frame extraction), `b34b3c922c` (h264 + format fix)**

The video bookmark pipeline received two substantial improvements. First: a download escalation ladder — standard yt-dlp → yt-dlp with `--impersonate chrome` → Opus subagent fallback for cases where the first two fail. ## Day 346: andy-core Goes Non-Root + Discord Gets a Model Registry (September 12, 2026)

### andy-core Container: Root → www-data

**Commits `04d7df2a61` (non-root setup), `fdf8607f0b` (pod opt-out), `46d6b02b50` (XDG roots), `9d2a0d54c1` (merge)**

The andy-core FrankenPHP container was migrated from running as root to running as uid 33 (`www-data`) throughout: FrankenPHP, supervisord, queue workers, and the PHP-FPM pool. The migration required four commits across a branch:

1. **`04d7df2a61`** — non-root setup with `userns_mode keep-id` so the host user maps into the container as `www-data`
2. **`fdf8607f0b`** — opt out of the default podman-compose pod so `userns keep-id` can apply (pods override userns)
3. **`46d6b02b50`** — make XDG config/data roots writable by www-data
4. **Merge** to main

Root cause: job wrappers were invoked with `-u www-data`, but FrankenPHP and workers were running as root — creating cache shard ownership conflicts where PHP wrote files owned by root that www-data couldn't overwrite. Running everything as www-data from the start eliminates the split. (This merge would cause an outage the next morning — see Day 347.)

### DiscordModelRegistry + Dynamic Model Buttons

**Commits `ce73d45b12` (registry), `733a45da85` (dynamic buttons), `42e45956f8` (labeling), `7dd42831` (handoff detection)**

The Discord bridge gained a `DiscordModelRegistry` service — a single source of truth for all model identities: API IDs, family names, human-readable labels, and button text. Before the registry, model detection and labeling were scattered across 12+ locations with inconsistent family-matching logic that misidentified certain models on continuation prompts.

The "Continue on {model}" button now reads the current model from the registry at render time — dynamic rather than hardcoded. When the handoff engine switches models across a session boundary, the new session's continuation buttons reflect the actual model running.

A companion feature: Discord reply references are now injected into the agent prompt (`ca51bf0d54`) — when a user replies to a specific Discord message, the quoted content is passed to the agent as explicit context.

### Memory Fully on Nomic + discord-checklist Skill

**Commits `e6acbcbc3a`, `eb6b1093e9`, `53e3161ab0`, `e5ca5f0465`**

Three remaining production memory recall paths were migrated to the nomic embedding endpoint (#649): `UserPromptSubmit` hook semantic search, `memory_suggestions` table, and the bridge auth header. All live search paths now query the nomic column; mxbai remains dual-write only.

A new `discord-checklist` skill was wired with 4 intent triggers, enabling checklist creation directly from Discord conversations. Four handoff fixes landed: `from_session_id` population corrected (wrong JSONL path), chattiness reduced via shared constant, AutoRename suppressed on continuations, document body suppressed during the handoff window.

**Lesson Learned:** A model registry is only worth building when the alternative has produced real bugs. A single source of truth for model identity eliminates an entire class of "which model am I on?" errors that are otherwise invisible until a continuation prompt misfires.

## Day 347: The Outage Recovery Marathon — Silent Alerts, Scheduler Drains, and Swap Pressure (September 13, 2026)

### The andy-core Outage and Recovery

**Commits `ddf92d1aa7` (auto-recovery), `bbdd664ec7` (container-bridge retry), `8792be44aa` (herdr restart guard)**

September 13 opened with an andy-core outage. Root cause: the non-root container merge from Day 346 introduced a startup race condition — the container-bridge's exec path ran before FrankenPHP workers were ready to receive requests. Three fixes in sequence:

1. **`bbdd664ec7`** — container-bridge retries exec once on startup race, bails on genuinely bad state
2. **`8792be44aa`** — herdr-server restarts no longer kill session-started containers (the restart was killing containers that were mid-session)
3. **`ddf92d1aa7`** — andy-core auto-recovery restored (the outage had disabled the watchdog path)

### Silent Job Alerts: The formatJobResult Bug

**Commit `3927b372ed`**

While triaging the outage, a second, older bug surfaced: job failure alerts had been silently disappearing since at least September 7. Cause: `formatJobResult` in the Discord notifier assumed its argument was always a string, but Bree passes an `Error` object for failed jobs. The function threw before posting to Discord — every job failure produced no alert at all, not a malformed one: silence.

Fix: type-check the argument; if it's an `Error`, extract `.message` and `.stack`. Paired with `76cecea558`: worker footers now rethrow the rejection (instead of calling `process.exit(1)`) so the Error reaches Bree's error event with a real stack trace — `exit(1)` had been discarding the stack entirely.

### Scheduler Shutdown Drain — 300 Seconds

**Commits `3ac147eb92` (drain), `5bba211613` (.clear()), `b8147439d6` (300s + backup guard), `9fd61100ea` (docs), `4956e8ae97` (28 job footers)**

The scheduler shutdown went from "kill everything immediately" to a proper 300-second graceful drain:

1. Bree marks the scheduler draining and stops accepting new jobs
2. In-flight workers run to completion (up to 300 seconds)
3. `pm2-safe-restart.sh` checks for an active backup before restarting — if a basebackup or WAL-prune is running, it refuses and requires `--force`
4. Bree timer handles cleared with `.clear()` — not `clearInterval`, which is a silent no-op on Bree's safe-timer handles

28 job runner footers were updated (`4956e8ae97`) to log the rejection before exiting, so at minimum the failure appears in the process log even if the Discord alert path has a bug.

### Backup Timeouts Extended

**Commits `2a6d0ab17c`, `dd6ed7bf7f`**

DO Spaces WAL prune batches now get 10 minutes (no explicit timeout before) with a 250-key cap per run. Tarball deletes get 10 minutes and sweep orphaned sidecar files accumulated from interrupted prior runs. Both timeouts were firing on large prune cycles as the backup archive has grown.

### Ollama Swap Pressure Fixed

**Commits `8f07b50058`, `71a1780740`, `60540dfad5`, `2530cfe2f1`**

Ollama's `keep_alive: -1` (keep forever) was causing 6.7GB of swap pressure — the loaded model never evicted. Fixed to `keep_alive: 2h`. The mxbai dual-write was paused to reduce embedding memory footprint. A nightly Ollama model flush was added at 4am ET to force eviction on a schedule, with the Discord notification corrected to `#system-notifications` (the previously configured `#server-health` channel doesn't exist).

### Three More suggest-options Fixes, /now Decisions, and Fable Injection

**Commits `b960db3c03`, `683a39b3ae`, `10a47091af`, `4e4c6085fa`, `c4b981cbfe`**

Three more text-before-buttons loss paths were closed in suggest-options. The stream event handler's turn-state counter was reset after each non-suggest-options tool call, preventing state bleed across invocations. The stream-suggest-options handler was gated to fire only after tool output arrives — preventing premature fires when tool calls are queued but not yet executed.

The `/now` snapshot was enhanced to surface recent decisions from the memory-catcher, giving the morning brief context from recent tool-use sessions.

A new hook (`c4b981cbfe`) automatically injects the disk-pattern analysis into every Fable agent invocation — ensuring Fable always has current disk pressure data when doing deep code traces. The model-delegation SOP was updated with Fable trace rules to prevent context blowout. The jfdibot-post daily job was disabled (`2c2faff62f`) — the approval-first rewrite decoupled posting from the scheduler trigger.

**Lesson Learned:** A bug that produces silence instead of an error is the hardest kind to notice. The `formatJobResult` crash was swallowing *all* job failure notifications — the symptom (no alerts) looks identical to "all jobs are succeeding." Silence is not evidence of health. Every error handler that might fail should be wrapped in its own try/catch.

## Reflection: Week 47

---

### The Mistakes We Made

#### 1. andy-core Non-Root Container Introduced a Startup Race

**Cost:** The Day 346 non-root migration merged to main and immediately caused a September 13 morning outage. The container-bridge was exec-ing into the container before FrankenPHP workers were ready — a timing race that didn't surface in testing because the container was already warm.\
**Fix:** `bbdd664ec7` retry on startup race; `8792be44aa` herdr restarts no longer kill live containers; `ddf92d1aa7` auto-recovery restored.\
**Lesson Learned:** Container security migrations that change process ownership need explicit cold-start testing. A warm-container test is not sufficient to verify cold-start behavior.

#### 2. formatJobResult Had Been Silently Swallowing Job Failure Alerts Since September 7

**Cost:** Every scheduled job failure from September 7 onward produced no Discord alert — 6+ days of silent failures. The notifier function crashed on `Error` objects without logging the crash.\
**Fix:** `3927b372ed` type-check before string methods; `76cecea558` worker footers rethrow instead of `exit(1)` so Bree's error event receives the real Error.\
**Lesson Learned:** A monitoring system that crashes silently when receiving errors is worse than no monitoring. Error handlers need to be more robust than the code they're monitoring — if the handler can throw, it will throw on the inputs that matter most.

---

### The Surprising Things

#### 1. jfdibot's Autonomous Path Was Reversed 48 Hours After Shipping

**Expected:** Autonomous posting (≥80% confidence) would be the primary flow with approval as a fallback.\
**Actual:** Two days after shipping, the autonomous path was removed entirely. The rate limit was hit before the first confident post completed the full pipeline. "Working in a test run" wasn't the same as "confirmed end-to-end in production." The correct sequence is: manual approval first → calibrate voice and format → then confidence-gated autonomy.

#### 2. Ollama keep_alive:-1 Had Been Creating 6.7GB of Swap Pressure for Weeks

**Expected:** Models evict naturally when not in use.\
**Actual:** `keep_alive: -1` means "never evict." The model was permanently pinned in RAM + swap since Week 41 when `keep_alive` was first set. The 6.7GB pressure had been accumulating for weeks, unnoticed because the server remained functional.
