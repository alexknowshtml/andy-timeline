### Discord Threads Become Self-Contained

**Commit `4b1c29a3f`**

When the Discord bridge creates a new thread from a message, it now reposts the original message inside the thread at creation time. Previously, anyone landing in the thread had no context for what started the conversation — that message lived only in the parent channel.

**Lesson Learned:** A thread without its founding message is an answer without a question. Make threads self-contained from the first reply.

### dangerous-command-guard: Token Leak Closed

**Commit `adfb282d2`**

The dangerous-command-guard now blocks inline Discord tokens in `curl` Authorization headers. The pattern `curl ... -H "Authorization: Bot <actual_token>"` embeds the credential directly in the command string, which gets stored in the session transcript. The fix: detect the pattern pre-execution and reroute to the approved variable-substitution approach.

**Lesson Learned:** A token in a shell command string is a token in the transcript. Guard the pattern, not just the destination.

## Day 270: Lifecycle Machine and Defensive Infrastructure (June 28, 2026)

### spawn-lifecycle XState Machine: Phase 2 and Phase 3

**Commits `513048dd4`, `f7274eca3`**

The day after spawn-async was decomposed, its lifecycle got a formal state machine. Phase 2 (`513048dd4`) introduced the XState machine itself with unit tests — a typed definition of every state a spawn session can be in and every transition between them. Phase 3 (`f7274eca3`) deployed it in shadow mode.

Shadow mode means the machine runs in parallel with the existing imperative code. It observes every state transition and predicts what state it would assign — but takes no action. Wherever the shadow's prediction diverges from actual behavior, there's a gap: either a missing state, an unmodeled transition, or an invariant the imperative code violates silently. Shadow running is the correct introduction strategy: validate completeness in production before the machine becomes authoritative.

**Lesson Learned:** Introduce state machines in shadow mode before takeover. Two to three weeks of parallel observation surfaces edge cases that unit tests can't cover, because unit tests can only test scenarios you've already imagined.

### ANDY_BENCH: Systematic Sandbox Hardening

**Commits `750fc6977`, `cf5314f6e`, `8a132a887`, `c037275b6`**

The ANDY_BENCH infrastructure — an environment variable guard that prevents sandbox test runs from touching production services — was extended across four commits across June 27-28:

- `ANDY_BENCH=1` guard added to the discord-notifier (June 27)
- `ANDY_STATE_DIR` env override added for isolating sent-email-sync state in tests
- `ANDY_BENCH` guard added to the `/send-to-discord` command
- Hard guards added to two previously unguarded production paths

The last commit is the telling one: "two unguarded prod paths" discovered after the initial guards landed. Those paths could have posted to Discord or mutated production state during a sandbox run.

**Lesson Learned:** Safety infrastructure requires an exhaustive enumeration pass, not incremental discovery. Enumerate every production-touching call site before writing the first guard — not after.

### SSH Pre-Guard Hook

**Commit `458f1001f`**

A PreToolUse hook was added that fires before any SSH connection attempt. The hook surfaces intent detection — if a message pattern matches an SSH intent, the skill warning appears reminding to check the Quick Reference table before connecting. This extends the dangerous-command-guard pattern to SSH: intercept before the action, not after the failure.

**Lesson Learned:** Safety hooks deliver value at pre-emption, not remediation. A warning before the command runs costs nothing. An error message after an SSH attempt to the wrong host costs time and trust.

### person-researcher Phase 3: Anomaly and Flag Detection

### Scheduled-Job Templates Archived

### relationship-refresh: Mode Inference Fix

**Commit `6a9060315`**

A bug in `/refresh-relationships` caused it to infer the wrong operating mode when audit files were present in the working directory. The fix prevents mode inference from audit files entirely — mode must come from explicit parameters, not from the ambient file state of wherever the skill is run.

**Lesson Learned:** Inferring operating mode from ambient filesystem state is fragile. The same skill run from two directories should produce the same default behavior.

### /issue Skill: One Router, Three Commands Retired

**Commits `7e2260bef`, `5bb39522d`**

Three overlapping slash commands — `/bug`, `/new-issue`, and `/issue` — were collapsed into a single router skill (`/issue`). The three had diverged in behavior over time, creating inconsistency in how GitHub issues were created and which duplicate-detection guards ran. The single router enforces consistent guards regardless of issue origin.

`to-issues` was renamed to `prd-to-issues` to clarify its scope: it converts PRDs to GitHub issues, not arbitrary task lists. The rename makes the skill's contract explicit.

**Lesson Learned:** When multiple commands do the same thing, they inevitably diverge. One router with clear routing logic eliminates silent behavioral inconsistency.

## Reflection: Week 36

---

### The Mistakes We Made

#### 1. ANDY_BENCH Guards Discovered Reactively

**Cost:** The initial ANDY_BENCH infrastructure missed at least two production call sites (`8a132a887` — "add hard ANDY_BENCH=1 guards to two unguarded prod paths"). A sandbox test run could have posted real Discord messages or mutated production state through those paths.\
**Fix:** Systematic audit of every production-touching call site.\
**Lesson Learned:** Safety infrastructure requires exhaustive enumeration before the first guard is written. Building guards reactively as paths are discovered means there's always one more you haven't found yet.

#### 2. spawn-async Re-export Broke Immediately After Step 4

**Cost:** `6ea5fc52e` (fix: re-export resubmitAfterCompaction from claude-process) was needed the moment step 4 landed — a reference that worked in the monolithic file broke when the dependency moved to a new module without updating the public interface.\
**Fix:** One-line re-export to restore the public interface.\
**Lesson Learned:** After each module extraction, audit every public import immediately. Don't batch-verify at the end of a refactor session — the gap between extraction and verification is where regressions hide.

---

### The Surprising Things

#### 1. spawn-async Steps 6-9 Each Took Under 4 Minutes

**Expected:** Extracting four modules from a complex async spawn pipeline would require careful dependency-graph review before each step.\
**Actual:** Steps 6-9 all landed between 14:43 and 14:53 — ten minutes for four extractions. Once the pattern was clear (find function, create file, update imports, verify), each step was purely mechanical. The hard work was steps 4-5; everything after was execution.

The pattern lock-in effect: discovery takes time, execution does not.

#### 2. ChatPanel Shed 26 Concerns in 3.5 Hours

**Expected:** Extracting 15 custom hooks plus 3 components from a large React component would span multiple sessions due to hook dependency ordering and the risk of circular references.\
**Actual:** L-series first (stateless utilities, no hook dependencies, any order works), M-series second (hooks in bottom-up dependency order), component shells last. The sequencing constraint eliminated circular dependency risk entirely. The full session ran 16:26 to 19:57 — 3 hours 31 minutes, 26 commits.

When you have the right extraction sequence, a monolith falls apart fast.
