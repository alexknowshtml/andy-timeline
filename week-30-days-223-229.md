### PM2 Crash-Loop Protection: host-bridge + jfdi-reader

**Commits `02240fabd`, `fb6808987`**

Bun 1.3.13 SIGTRAP panics were taking host-bridge down every ~13s during fork-storm conditions. Default PM2 `min_uptime` of 5s let the restart counter reset between crashes, so services looped indefinitely. Today's incident: jfdi-reader hit **58 restarts in minutes** when Bun 1.3.14 SIGTRAPed during spawn pressure, wedging PM2 tracking into a `pid=null/status=online` zombie state requiring a nuclear restart.

The fix shape (both services):
- `ecosystem.config.cjs`: `min_uptime=60s`, `restart_delay=5s`
- `pm2-safe-restart.sh`: `--restart-delay 5000 --max-restarts 10`
- PM2 CLI has no `--min-uptime` flag — only available via JSON config

The underlying Bun panic is unfixed (1.3.14 still crashes); this just keeps PM2 from compounding the damage by fork-storming.

### The Mistakes We Made

#### 1. Bun 1.3.13 + Default PM2 Restart Behavior = Fork-Storm

**Cost:** jfdi-reader hit **58 restarts in minutes** when Bun 1.3.14 SIGTRAPed during spawn pressure, wedging PM2 tracking into a `pid=null/status=online` zombie state that required a nuclear restart. host-bridge had the same problem on a slower cycle (~13s crash interval). PM2's default `min_uptime=5s` let the restart counter reset between crashes, so the service looped indefinitely instead of stopping after `max_restarts`.\
**Fix:** `02240fabd` (host-bridge) + `fb6808987` (jfdi-reader) — `min_uptime=60s`, `restart_delay=5s`, `--max-restarts 10` (CLI has no `--min-uptime` flag, only JSON config). Underlying Bun panic is unfixed (1.3.14 still crashes); the protection just stops PM2 from compounding the damage.\
**Lesson Learned:** PM2's default restart behavior is *optimistic* — it assumes most crashes are transient. When the underlying runtime is panicking (Bun SIGTRAP), optimistic restart turns a single crash into a fork-storm. Set `min_uptime` >= 30s on any service that talks to a runtime version known to be unstable, and never use `--max-restarts` without `--restart-delay` (CLI defaults will undermine the cap).

#### 2. The Calibration Offset That Was Right Until It Was Wrong

**Cost:** sound-viewer applied a -2.7 dB calibration offset (`bfb320c9d`) to align the M5 mic with the Minut 3rd Floor sensor — then **removed it** (`f96f4306d`) three hours later because the M5 was reading correctly without it.\
**Fix:** `f96f4306d` — Remove the -2.7 dB offset.\
**Lesson Learned:** Calibration against another sensor is only as good as the reference sensor's accuracy. The "right" offset is the one that matches *physical reality* (a known dB source), not the offset that matches another reading device. The two iterations cost an evening but proved the M5 mic was the more trustworthy reference all along.

#### 3. NLBID ED Doc: One Document Wasn't Two Audiences

**Cost:** The Saturday detailed ED responsibilities breakdown (`6b19da5b9`) tried to serve both the board's review needs and the operational reference role — accountability tiers, time allocation, budget ratios, accountability framework, full 10-function breakdown all in one doc.\
**Fix:** `2abd16a59` — Split into two files: board overview (leaner for board review) + responsibilities reference (full base document). Plus AI slop removal (`8c9fb80dd`), cross-doc reference note removal (`395f1a46c`), em dash replacement (`ab403fd01`).\
**Lesson Learned:** One audience per document. A board doc that *also* serves as an operational reference will be too long for the board and too compressed for operations. When a doc accumulates both numbered framework + tiered accountability + 10-function detail, that's the signal to split.

#### 4. The Brivo `change-state` Path Bug (Door ID vs Schedule ID)

**Cost:** The `change-state` command was using the schedule ID instead of the door ID, causing requests to fail until the path was corrected.\
**Fix:** `eb0b3c73c` — Fix `change-state` path: door ID not schedule ID.\
**Lesson Learned:** API surface research is the time to verify identifier-shape assumptions, not at the command-implementation step. The Brivo command-by-command pass should have included a "what identifier does this endpoint expect" probe as step 1 for each command.
