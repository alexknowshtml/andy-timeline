## Day 316: Three Watchdogs, One Podman Safety Pin (August 13, 2026)

### Sonos Auto-Recovery Watchdog

**Commit `ca1c1ec0c2`**

The Sonos Controller has a known failure mode: the NIC locks up under load, dropping audio without raising an error. You built an auto-recovery watchdog that detects the lockup, triggers a 5-minute NIC drain (not an immediate power cycle — rushing the drain causes a second lockup), and resumes playback with shuffle on. A companion commit (`8b55f6b487`) added the stability refinements after the first test run caught the timing gap.

### system-watchdog: Tiered Whitelist + Advisory Monitoring

**Commits `40db188cee`, `53cf868b47`, `de71fac135`, `79fb0dda93`**

The system-watchdog had been firing false positives on the ollama process — a known memory hog that's expected under load. Four commits across the day tightened it: tiered whitelist logic (different rules for known-heavy vs expected-light processes), ollama advisory fires only when swap is also elevated (not just RAM), advisory rate-limited to once per hour (resets on OK), and the Claude session limit raised from 6 to 8 to match production load patterns.

### Subagent Last-Action Preview

**Commit `4ad4ebf0ab`**

The subagent progress panel now shows the last tool action description in real time. During long subagent sessions, the panel had shown "running" with no indication of what the agent was actually doing. The last-action description gives the watcher — and Alex — a live signal without requiring session transcript reads.

### Podman Subnet Pin

**Commit `54a384fc28`**

A subtle production risk was closed: Podman's network subnet was dynamically assigned, which meant it could change across restarts. The WAL receiver connects to PostgreSQL over the container network — a subnet change would silently break replication. Pinning the subnet to a static CIDR makes the WAL path predictable regardless of container restart order.

**Lesson Learned:** Auto-assigned network addresses are a hidden dependency. Any service that connects to a container by IP (not DNS) inherits the assignment's fragility. Static subnets are a one-time cost that eliminates a class of mysterious post-restart failures.

## Day 319: Work Orders Day — Four Delivered in One Session (August 16, 2026)

### Overview

August 16 was the most productive single day since the Pane Pool week. The Work Orders system — a fully formalized delegation lifecycle for Fable-reviewed agent tasks — went from zero to four delivered work orders in one sustained session. Alongside it: a 7.5-month relationship data freeze was found and fixed, msgvault got a nightly cache rebuild and CLI wrapper, the Discord bridge shed a 49-line if/else dispatch block, and seven more scheduler jobs completed the GH #557 runWithGate migration.

### Work Orders: WO-001 through WO-004 Delivered

**Commits `fe67c9ca36` (DB + API), `82725fe1e5` (Fable REVISE gaps), `9bc30ded48` (runner), `d1321abf1f` (claimed state), `14d5bbe722` (lockForUpdate), `40b94a4f3b` (dispatch loop fix), `f35dc20e59` (skill), `eb0358d5f3` (intent triggers)**

The Work Orders system is Andy's formalized delegation layer — a state-machine-enforced workflow for pitching tasks to Fable, tracking review cycles, and dispatching execution to headless Claude sessions without requiring Andy to be in an active session.

**WO-001** built the foundation: a `work_orders` table with UUID PK, pitch_hash binding, content-hash approval gate, and jsonb fields for pitch/steps/review. A Fable REVISE cycle caught two gaps — the content-hash binding wasn't enforced through all state transitions, and the state gate had a hole where a claimed WO could be re-dispatched. Both fixed before PASS.

**WO-002** built the execution layer: `work-order-runner.cjs` runs in dual mode — triggered by webhook from the API on `approved` transitions, and hourly fallback scan for stalled WOs. The runner auto-generates a brief from pitch + context + steps + definition_of_done, spawns a detached Claude session, and patches to `dispatched` after successful spawn. A stall guard covers both `dispatched` and `claimed` WOs older than 24 hours, pinging Discord. Fable caught two bugs before merge: the runner was re-fetching after a successful PATCH (causing a false-failure state) and the `RECENT_THRESHOLD_MS` window for deduplication was too short.

**Claimed state** replaced the time-threshold dedup with a real state machine lock. Before spawning, the runner patches to `claimed`; concurrent hourly scans see `state=claimed` and skip. `lockForUpdate` makes the claim atomic — two concurrent runners can't both claim the same WO. A dispatch loop bug was also fixed: the webhook was firing on `claimed→approved` releases (failure path), which re-triggered the dispatch — the fix suppresses the webhook on that specific transition.

**The skill** (`f35dc20e59`) captured the full lifecycle — state machine, Discord templates, Fable gate protocol, dispatch gate nuance, claimed state, trust tiers — in 398 lines across four reference files. Twenty-five intent triggers (`eb0358d5f3`) wire it to conversational phrases so Work Orders are discoverable from natural language.

WO-003 and WO-004 were executed and delivered using the system itself, on the same day it was built.

**Lesson Learned:** A delegation system that uses itself to validate on day one is the only real test. Building the Work Orders system and then completing four WOs through it in the same session proved the state machine, the runner, and the Fable gate all work end-to-end under production conditions.

### Relationship last_contact: 7.5-Month Data Freeze Found and Fixed

**Commits `f4f8c5b02c`, `18745aa8f3`, `e9dd45ac31`, `0a598f1a61`, `57b7799cba` (128 files normalized), `6f96a216d2` (1035 freshness labels updated)**

A quiet data integrity bug that had been running since January 2026 was discovered and fixed. `verify-last-contact.py` was reading `last_contact` dates with `yaml.safe_load`, which preserves quotes when they're part of the value — so `"2026-01-15"` (with embedded quotes) was being written back as `'"2026-01-15"'` (double-quoted). On the next read, Python's date parser saw the outer quotes as part of the string and couldn't parse the date, so it fell back to a default — effectively freezing the contact's last_contact date at whatever it was before January 2026.

150 relationship files had frozen dates. 128 files were normalized (the others had already been touched by other scripts that didn't reproduce the bug). 1,035 freshness labels were recalculated across the full relationship database.

**Lesson Learned:** YAML round-trip through Python is not identity. `yaml.safe_load` parses `"2026-01-15"` as the string `2026-01-15` (without quotes), but `yaml.dump` may or may not re-add quotes depending on the value and the dumper's quoting rules. Reading with `frontmatter` and writing back with the dump step created a quoting mismatch that accumulated silently for 7.5 months.

### msgvault: Nightly Cache Rebuild + CLI Wrapper

**Commits `a006106925` (CLI wrapper), `8ebfe1ac69` (nightly job + skill update)**

The msgvault NAS email archive gained two additions: a `scripts/msgvault.sh` CLI wrapper that routes queries through the NAS search API without requiring users to know the endpoint format, and a nightly cache rebuild job that ensures the search index stays current. The research-map and search skill were updated to point to the wrapper.

### Discord Bridge: Route Table Replaces if/else Dispatch

**Commit `f30bb83e1c`**

The discord-bridge's command dispatch was a 49-line `if/else-if` chain that required touching the dispatch function every time a new command was added. It was replaced with a route table — a key-value map from command name to handler. New commands register themselves in the table; the dispatch loop is now O(1) and untouched by additions.

**Lesson Learned:** An if/else dispatch chain that grows to 49 lines is a smell, not a pattern. Route tables scale linearly in registration cost and stay constant in dispatch cost. The refactor also made the handler inventory visible at a glance — the old chain required reading every branch to know what was registered.

### Scheduler: Seven More Jobs, Alert Cooldown Unified, criticalJobs Names Fixed

**Commits `743b219b5a` (7 more runWithGate jobs), `bb60ff9cb3` (alert cooldown Map), `4630197430` (criticalJobs name fix)**

Seven more high-frequency Bree jobs completed the GH #557 runWithGate migration. The alert cooldown state was unified — two mismatched variables tracking the same state were replaced with a single Map. The `criticalJobs` names were corrected to match the actual `SyncRun` `job_name` values; the mismatch had caused alerts to fire on jobs that weren't actually critical, and miss jobs that were.

## Reflection: Week 43

---

### The Mistakes We Made

#### 1. Relationship last_contact Dates Frozen for 7.5 Months

**Cost:** 150 relationship files had their `last_contact` dates silently frozen at their January 2026 values. Relationship freshness scores, cold-outreach targeting, and the `/refresh-relationships` workflow were all operating on stale data — anyone contacted after January appeared more distant than they actually were.\
**Fix:** Commits `f4f8c5b02c` through `57b7799cba` — traced the bug to YAML round-trip quoting in `verify-last-contact.py`, fixed the parser to strip embedded quotes before date parsing, normalized 128 files, recalculated 1,035 freshness labels.\
**Lesson Learned:** `yaml.safe_load` is not a neutral read. Quoted string values survive the load step as unquoted strings, but the dump step may or may not re-add quotes — the result depends on the value's content and the dumper's quoting heuristics. Scripts that round-trip YAML must verify the write output, not just the read input.

#### 2. Work Order Dispatch Loop on claimed→approved Release

**Cost:** A failed WO claim (approved→claimed→failure→back to approved) triggered the webhook, re-dispatching the WO immediately. Without the fix, a transient runner failure would cause the WO to keep re-dispatching on every failed claim attempt.\
**Fix:** `40b94a4f3b` — suppressed the webhook on the `claimed→approved` release transition specifically.\
**Lesson Learned:** State machine webhooks should specify *which* transitions trigger them, not just *which* states they watch. A blanket "fire on approved" rule fires on any arrival at approved, including reversions from failed locks.

#### 3. Backup: Silent Failures and No Pre-Delete Verification

**Cost:** The DO Spaces backup pipeline had been running without alerting on non-zero exit codes and pruning old backups before verifying the new one was readable. In the worst case, a corrupted new backup could prune the valid old one silently.\
**Fix:** `261bcdf035` + `f380da838f` — added alerts on silent failures and gated delete on verified download-and-checksum.\
**Lesson Learned:** A pipeline that doesn't alert on failure looks the same as a pipeline that's succeeding. Silence is not health.

### The Surprising Things

#### 1. Four Work Orders Delivered the Day the System Was Built

**Expected:** Building a database, API, runner, and state machine takes multiple sessions. The first WOs would run the week after the system shipped.\
**Actual:** WO-001 through WO-004 were all pitched, reviewed by Fable, approved, dispatched, and delivered on August 16 — the same day as the foundational commits. The system validated itself under production conditions within hours of existing.

The Work Orders pattern had been informally in use for months (pitching tasks to Fable, running headless sessions). Formalizing the infrastructure took one day because the behavioral contract was already well-understood.

#### 2. The relationship Freeze Lasted Longer Than Any Other Silent Bug

**Expected:** Silent data integrity bugs get noticed when the data is used — a wrong freshness score, a missed cold-outreach target, something visible.\
**Actual:** 150 frozen relationship files ran undetected for 7.5 months. The freshness scores were wrong, but the wrongness was consistent — contacts who were "cold" stayed cold, which matched the expectation. The bug only surfaced when a specific contact's date was checked against a known interaction.

Silent bugs in slowly-changing data are harder to notice than silent bugs in fast-changing data. A frozen last_contact date in a system that checks contacts weekly drifts slowly enough that the drift looks like normal relationship cooling.
