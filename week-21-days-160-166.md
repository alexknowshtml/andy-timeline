## Days 161-163: Sleepme Integration Arc (March 11-13, 2026)

### Overview

Three days took Sleepme from "no integration" to an adaptive bed temperature system that reads the bedroom thermostat, applies time-of-day schedules, and runs autonomously every 15 minutes. Along the way, MQTT reverse engineering revealed the sleep tracker's raw sensor protocol.

### Day 1: CLI & Skill Foundation

**Commit `d4977294b`**

A 419-line TypeScript CLI wrapping the Sleepme Developer API shipped with commands for device status, temperature control, thermal on/off, brightness, sleep reports, and raw PATCH access. The skill file documented the full API surface.

### Day 2: Adaptive Scheduling with Ecobee Cross-Reference

**Commit `cdeb4e000`**

The adaptive bed temperature scheduler landed - a 259-line scheduled job running every 15 minutes. It reads the ecobee bedroom sensor and applies time-of-day targets: cool at bedtime, warm for wake-up, standby at 10am. The key insight: warmer room = cooler bed, cooler room = warmer bed. The offset calculation makes the bed respond to the room, not just the clock.

### Day 3: Dual Schedules & MQTT Discovery

**Commit `e7a21f983`**

The single schedule was replaced with dual warm-room/cold-room schedules, switching at a 70F ecobee threshold. Temperature calibration corrected to 100F max (not 110F). MQTT traffic analysis revealed the sleep tracker publishes 193-byte sensor payloads every 10 seconds to an AWS IoT Core broker on port 8883, with 31-byte keepalives every 2 minutes. Phase 5 (direct MQTT integration) was added to the plan.

**Lesson Learned:** Hardware integrations benefit from a layered approach: API first (works immediately), schedule automation second (adds intelligence), and protocol-level integration third (adds real-time data). Each layer is independently useful.

## Day 162: The 27,000-Error Discord Fix (March 12, 2026)

### Discord Duplicate Response Root Cause

**Commit `018d2210c`**

The biggest bug fix of the week. Status callbacks from Andy Core's `updateStatus()` were making synchronous 10-second HTTP calls back to host-bridge, exhausting all 16 FrankenPHP worker threads during active sessions. This caused 27,000+ 503 errors and incremental edit failures that fell back to posting duplicate messages.

The fix restructured the status flow architecture:
- Host-bridge now edits Discord status messages directly via the bridge CLI (3-second timeout)
- Andy Core's `/api/discord/status` became cache-only (heartbeat + busy flag refresh)
- The busy flag now refreshes on every non-terminal status update, fixing a 60-second TTL expiry issue
- Incremental edit fallback retries once, then posts only the new chunk (not full text)

### Small Talk Newsletter Shipped

**Commits `bcd6fe248`, `2856f5002`, `a4963d1bb`, `204b73780`, `f4cb4c4d1`, `fbc427e53`**

The Small Talk newsletter for March 13 went from draft to scheduled broadcast (23272174) in a single session. Neil's KMart Radio find replaced a generic members section. The Good Neighbors link was corrected to indyhall.org.

### Busy Flag Cache Key Bug

**Commit `476b3836a`**

The busy flag refresh was using channelId instead of threadId as its cache key, meaning the "Andy is typing" indicator was being set on the wrong context. A one-character category of bug with outsized user-facing impact.

### Debugging SOP Enhancement

**Commit `da9e4cb75`**

The blocking HTTP cascade pattern from the duplicate response investigation was documented in the debugging SOP, so future similar issues can be diagnosed faster.

**Lesson Learned:** When service A makes synchronous calls to service B which calls back to service A, you have a thread-exhaustion time bomb. The fix is always the same: make the callback async, or move the work to the side that doesn't need a callback.

## Reflection: Week 21

---

### The Mistakes We Made

#### 1. Discord Status Architecture Was a Thread-Exhaustion Time Bomb

**Cost:** 27,000+ 503 errors and duplicate Discord messages from exhausted FrankenPHP worker threads. The synchronous callback pattern had been in place since the Discord integration launched.\
**Fix:** `018d2210c` - Moved status editing to host-bridge, made Andy Core's status endpoint cache-only\
**Lesson Learned:** Synchronous HTTP calls between services that call back to each other will always eventually exhaust threads. The question is when, not if.

#### 2. Partial Sync Monitoring Created Blind Spots

**Cost:** 43 of 55 scheduled jobs had no stale detection, and 6 dead jobs were still in the database creating noise\
**Fix:** `bd355a1f7` and `bc7b877a5` - Full job catalog with frequency-aware stale thresholds, dead job purge\
**Lesson Learned:** Monitoring 22% of your jobs and calling it "monitoring" is worse than no monitoring at all - it creates false confidence.

#### 3. Regex Parsing of Human-Readable Output

**Cost:** Task digest broke when the PM agent changed its heading format from `### #1:` to `### 1.`\
**Fix:** `f11f23a90` - Structured JSON sidecars instead of markdown parsing\
**Lesson Learned:** Never parse formatted output with regex when you control both the producer and consumer. Use a structured interchange format.

### The Surprising Things

#### 1. QMD: 54,000 Embeddings in One Session

**Expected:** Embedding 16,000+ files would be a multi-day project requiring careful batching\
**Actual:** qmd v2.0.0 handled the full repo embedding in one go, and the scheduled job keeps it current with hourly refreshes

The embed loop's crash resilience (auto-restart on failure, position tracking) made the 4am backstop a safety net rather than a requirement.

#### 2. Sleepme MQTT: Hardware Talks More Than Expected

**Expected:** The sleep tracker would be a closed system with only the cloud API for data\
**Actual:** MQTT traffic analysis revealed 193-byte sensor publishes every 10 seconds - rich real-time data flowing through an accessible protocol

The path from "I want to control my bed temperature" to "I can read raw sensor data" took exactly 3 days.

#### 3. The Busy Flag Was Wrong This Whole Time

**Expected:** The "Andy is typing" indicator was working correctly\
**Actual:** A channelId/threadId cache key mismatch (`476b3836a`) meant the busy flag was being set on the wrong context. A single-character-category bug that had been silently wrong.
