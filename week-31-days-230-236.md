## Overview: The Infrastructure Layer That Changes Everything

Week 31 was a singular build: the **Claude Pane Pool** — a Podman container running persistent Claude Code sessions in tmux panes with an HTTP router on port 2650 — went from a Monday evening design doc to a production service routing all scheduled jobs by Friday. The problem it solves: every scheduled job previously spawned a fresh `claude` process, and under concurrent load the server hit EAGAIN fork-rate limits. The pool eliminates spawning entirely — prompts go in via HTTP, results stream back via SSE, and sessions persist across jobs.

The build arc was relentless: Monday night produced the container + HTTP router. Tuesday was 135 commits — early completion via transcript watcher (62s → 2s), state persistence, session continuation, /health + /metrics endpoints, graceful drain, recovery sweep, a full debug UI with SSE log, subagent transcript injection, and iOS Safari compatibility. Wednesday refactored the 800-line server into 8 modules, added per-prompt model selection, disk-based crash recovery, and built the `pool-ctl` CLI for job routing management. Thursday promoted 8 jobs to live and built Pi integration extensions for cross-tool compatibility. Friday built the **EOD Pipeline** on top of the pool — a multi-model architecture where Haiku/Sonnet subagents gather data in parallel and Opus synthesizes the daily brief. Saturday wired the Discord bridge directly into pool sessions for turn-by-turn streaming.

Parallel to the pool build: a **supply chain hardening pass** pinned dependencies to exact versions across 12 repos and patched 16 CVEs in Andy Core's Composer dependencies. Two Pi extensions shipped (transcript JSONL and Claude Code hooks). The **TaskCreate/TaskUpdate** migration replaced TodoWrite system-wide. And Virginia Tufte's *Artful Sentences* became Andy's newest style guide section.

**Key themes:** Claude Pane Pool (design → production in 6 days), EOD Pipeline (Haiku/Sonnet/Opus multi-model), supply chain hardening (dep pinning + 16 CVE patches), Pi integration (transcript + hooks extensions), pool-routing migration (8 jobs live), TaskCreate/TaskUpdate system-wide migration, Artful Sentences style guide, Discord panepool channel with turn-by-turn streaming, triage-tasks improvements, /flowchart skill, scheduled-jobs SOP rewrite for pane pool era.

## Reflection: Week 31

---

### The Mistakes We Made

#### 1. The EOD Single-Pass Design (Attempted and Reverted)

**Cost:** The first attempt at migrating the EOD brief to the pane pool used a single-pass design — send the entire prompt at once and hope the model gathers all data in one shot. This produced incomplete briefs because a single prompt can't reliably orchestrate 6+ data sources without losing context. Committed (`d5377b60`), then reverted (`eef0a5e5`) within 20 minutes.\
**Fix:** Redesigned as parallel subagents (Phase 1) feeding a synthesis pass (Phase 2). Each agent handles 1-2 data sources independently.\
**Lesson Learned:** Any pipeline touching 4+ data sources needs explicit parallelism — a single prompt asking "gather all this" will always drop something. The cost of the revert was low (20 minutes), but the design insight was high: gathering and synthesis must be separate phases.

#### 2. Model Switch Race Condition

**Cost:** Pool-routed jobs requesting a specific model (e.g., Opus for EOD synthesis) would sometimes have their prompt swallowed — the prompt arrived before the model switch completed, getting lost in tmux's buffer. Multiple fix attempts (`56e6e51a`, `22b576e0`, `86816954`) before the reliable pattern emerged.\
**Fix:** `sendLiteralWithRetry` — wait for model switch output confirmation, then send prompt with retry on failure.\
**Lesson Learned:** tmux is not a message queue. Sequential operations (switch model → send prompt) need explicit synchronization, not timing assumptions. The 50ms delay that "worked in testing" fails under real concurrency.

#### 3. Container Mount Discovery by Failure

**Cost:** Five separate commits (`5c1587e5`, `379141035`, `e769cc2d`, `90dcad4a`, `1bd84c47`) adding mounts that pool-routed jobs needed but the container didn't have — /home/linuxbrew, gh config, gogcli config, ~/.local/bin, permissions bypass. Each discovery meant a job failed in production before the mount was added.\
**Fix:** Each mount added as it was discovered. No pre-audit was done.\
**Lesson Learned:** When migrating workloads into a container, do a "what does this job actually touch" audit for each job *before* routing it, not after. A 5-minute `strace` or `lsof` run on each job would have caught all 5 missing mounts in one pass.

#### 4. The Assistant Turn Posting Filter Flip-Flop

**Cost:** Discord bridge initially posted only `end_turn` assistant messages (`b8748099`). Then reversed to post all assistant turns (`d6ea4da6`) after discovering intermediate reasoning was wanted. Then added the `tool_use` skip back. Three commits to get the filter right.\
**Fix:** Final state: post all assistant turns except those containing only tool_use content blocks.\
**Lesson Learned:** Streaming UX decisions need a "watch someone use it" step before committing to a filter. The correct filter was neither "all" nor "end only" — it was "all except pure tool_use noise." This middle ground only becomes obvious by watching real output.

### The Surprising Things

#### 1. 135 Commits in a Single Day (Tuesday, May 20)

**Expected:** The pane pool build would be a multi-day grind with each piece landing incrementally across the week\
**Actual:** Tuesday produced 135 commits — the most in any single day in the project's history. The forcing function: every scheduled job was still hitting EAGAIN intermittently, creating urgency to get pool routing live.

The compounding lesson: urgency + clear architecture (design doc done Monday night) + single-focus day = velocity that would take a week spread across interruptions. The pane pool could not have been built in 1-hour increments.

#### 2. The Debug UI Became the Primary Development Tool

**Expected:** The debug UI (`9eb4c8f0`) would be a nice-to-have diagnostic page\

Every subsequent feature (model selection, EOD pipeline, Discord streaming) was developed while watching the debug UI. By Thursday, the UI had test prompt buttons, suggest-options simulation, and a TodoWrite panel.

The compounding lesson: invest in observability UI *before* building the features that run on the infrastructure. The 2 hours spent on the debug UI saved 10+ hours of printf debugging over the rest of the week.

#### 3. Pi Integration Was Surprisingly Simple

**Expected:** Making Pi (a completely different AI tool) emit Claude Code-compatible transcripts and fire Claude Code hooks would require deep compatibility work\
**Actual:** Two extensions (`69b09be4`, `2174846f`) — one for transcript JSONL, one for hooks — and the entire Andy toolchain (session-forensics, insight extraction, audit quality review) works on Pi sessions. The key insight: Claude Code's hook protocol is simple enough (JSON stdin/stdout with a `type` field) that any tool can implement it in ~100 lines.

#### 4. Haiku Is Good Enough for Data Gathering

**Expected:** The EOD pipeline would need Sonnet for all data gathering to maintain quality\
**Actual:** Agent 1 (Discord messages + email threads) runs on Haiku and produces equivalent output to Sonnet for structured data extraction. The cost savings are significant — Haiku is 10x cheaper per token. The boundary: Haiku works for "read this and extract fields" but fails at "read this and decide what matters." Phase 2 synthesis still needs Opus.
