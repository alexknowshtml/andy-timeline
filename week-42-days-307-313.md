## Day 311: herdr Graduates, Five Databases Covered, Drone Clearance Skill (August 8, 2026)

### herdr 0.8.0: PM2 to systemd, Patched Pipeline Retired

**Commits `db1ffc5aea` (migration path + PM2 fix), `20ce490390` (Type=forking → simple), `9ee78ee2b1` (rogue server takeover), `274768cda1` (#500 pipeline retirement), `30cc2b81f0` (rename), `52e6278019` (SOP update)**

The herdr upgrade arc that started in Week 41 closed on August 8 with two coordinated changes landing together.

**The systemd migration (#530)** replaced the PM2 daemon with a proper systemd user unit. The migration had a subtle failure mode: herdr clients auto-spawn a server when none is detected. A client running during the migration window spawned a server before systemd claimed the socket — causing `systemd start` to hit "already running" and loop in restart-failure. The fix (`9ee78ee2b1`) makes the start script take over from a rogue server: it kills a herdr-owned socket holder and claims the socket, while still refusing to kill non-herdr processes. The unit type was also corrected from `Type=forking` to `Type=simple` (`20ce490390`) — herdr doesn't fork; the wrong type caused systemd to wait for a child that never appeared.

**The patched pipeline retirement (#500)** closed the fork CI workflow, patched update mode, and release-watch dispatch logic that had kept Andy on a custom herdr fork. The 0.8.0 upgrade made the tab-target-label fork patch unnecessary — jfdi now targets panes by ID. `herdr-update.sh` becomes stock-only; step 2c regenerates `.claude/skills/herdr/SKILL.md` from `herdr --skill`. The bundled skill file (`274768cda1`) replaces the hand-maintained one. The fork workflow on alexknowshtml/herdr is disabled but not deleted — history stays browsable.

The binary is renamed `herdr-real → herdr-custom` to reflect intentional customization rather than a patching workaround.

**Lesson Learned:** The fix-and-revert from Week 41 did exactly what it was supposed to: hold the gate until both sides could ship together. The coordination cost was explicit; the revert preserved working state until the bundled deploy was ready.

### Backup PITR Extended to All 5 Databases

**Commits `47443f151110` (WAL + base backup extension), `0947e3f2f199` (pg_dump extension), `9222bf30f310` (docs update)**

The Week 41 restore test proved PITR worked for `andy_core`. August 8 extended the same architecture to all five app databases: `andy_core`, `trackmeet`, `hall_monitor`, `markdawn`, and `documenso`.

- **`wal-receiver-multi.sh`:** Single script handles any DB via `$1`; PM2 runs 5 separate `wal-receiver-<dbname>` services
- **`backup-pg-basebackup.cjs`:** Loops over all 5 DBs independently — per-DB failure alerts without blocking successful DBs; per-DB Spaces keys, WAL-start sidecars, GFS retention, WAL pruning
- **`sync-wal-to-spaces.cjs` and `monitor-wal-lag.cjs`:** Updated for per-DB paths and per-slot monitoring
- **`markdawn` quirk:** Pasta networking means the host connects as `65.21.54.221` — documented in the per-DB connectivity notes

**Lesson Learned:** Once a backup architecture is proven for one database, extending to N databases is path parameterization. The hard architectural work (WAL streaming, GFS retention, restore runbook) was done once in Week 41. August 8 was mechanical.

### /airspace Skill: Drone Clearance in Plain English

**Commits `0519fd6b7f` (skill + script), `d6a1117756` (25 intent triggers)**

A new `/airspace` skill checks whether drone flights below 400ft AGL are clear at any US address. `airspace-check.sh` geocodes the address via Nominatim, queries the OpenAIP airspace API with a bounding box, and returns a plain-English verdict: Class G = clear, anything else = LAANC required. 25 intent triggers wire it to conversational phrases like "can I fly my drone here?" without needing the explicit slash command.

**Lesson Learned:** A skill with 25 intent triggers is as discoverable as a conversational feature. The trigger list is the UX — if the skill can't be found through natural language, it effectively doesn't exist.

### Morning Context: Sent Email as Resolution Evidence

**Commit `b388cdf292`**

The morning-context generator now fetches the last 2 days of sent email from Gmail before synthesizing the daily brief. Items flagged as "outstanding" in EOD briefs are cross-checked against sent email — if Alex emailed the relevant person after the item appeared, it's treated as actioned rather than open. A companion fix (`a2c19f543b`) verified outstanding items against live data before asserting them as unresolved.

**Lesson Learned:** Outstanding items need resolution evidence, not just detection. Sent email is the most direct signal that something was acted on — it proves external communication happened, which task status alone doesn't.

### spawn-utils: Duplicate Discord Post Fix

**Commit `03001850c609` (GH #527)**

`extractTextFromStreamJson` was joining text from every assistant turn with `\n\n`. When Claude emits text before a `tool_use` and then again after a meta-inject (`[Your previous response had no visible output]`), both blocks landed in the Discord post as a duplicate. The fix: return only the last `end_turn` text block, with a `lastTextBlock` fallback for sessions that end mid-tool.

**Lesson Learned:** The meta-inject fires after a thinking-only turn, leaving the pre-tool text block in the output buffer alongside the final `end_turn` text. Multi-turn output accumulation needs a "last wins" policy, not concatenation.

## Days 312-313: TikTok Transcription Breakthrough and Discord Gets Task Eyes (August 9–10, 2026)

### TikTok Auto-Transcription via Mac Mini Proxy

**Commits `b0d1224fea` (transcription path), `1e871b337a` (transcribe-first order)**

TikTok is geo-blocked on Hetzner — `yt-dlp` fails with exit code 10231. The fix: download via the Mac mini at `100.78.238.106` over Tailscale, scp the file back to the server, run `transcribe-smart.sh`, and append `## Video Notes` to the reference file. Simultaneously, the filing order was flipped to transcribe-first (`1e871b337a`): the transcript is generated before the summary and tags are written, so content informs classification rather than the classification preceding the content.

**Lesson Learned:** A geo-block isn't a dead end — it's a routing problem. The Mac mini already handled voice memo pre-staging; adding TikTok download as another proxy task required no new infrastructure, just a new path through existing infrastructure.

### Session-Start: Daily Context Without API Calls

**Commit `274a0d51fc`**

The session-start checklist gained a Step 0: load `alex-current-context.md` before anything else. The daily snapshot is now wired into every session start, giving fresh agents current strategic state without live API calls or knowledge of the memory/cold-storage split. ### Discord Live Task Embed: From Invisible to Tracked

**Commits `afbd9b6448` (live todo embed), `479dff6ba5` + `2545c0a7f2` (async path fix), `775e7fcc86` (insertion order), `8737f05858` (spinner attachment), `15d30954d4` (eject on stop), `f09b06efb5` (teardown restore + deleted status)**

When a Discord-driven session uses TaskCreate/TaskUpdate/TodoWrite, the thread was previously silent — tasks moved through states with no visibility. August 9-10 fixed this in two phases:

**Phase 1 (Aug 9) — Live todo embed:** The JSONL stream parser in `spawn-sync.ts` watches for task tool calls and posts a single embed to the thread on the first TaskCreate. Every subsequent update edits the same message in-place. Tasks show pending → in_progress → completed; the embed turns green when all tasks finish and stays as a turn receipt. A bug fix landed immediately: the embed was being posted from the wrong async path (`stream-processor.ts`, the web path) instead of `spawn-sync.ts` (the Discord spawn path) — moved correctly in `479dff6ba5` and `2545c0a7f2`. Insertion order was preserved with a fix (`775e7fcc86`) after tasks were appearing out of sequence.

**Phase 2 (Aug 10) — Spinner attachment:** The task panel was wired to travel with the spinner during processing. Each TaskCreate/TaskUpdate patches the active spinner message to include the embed alongside the braille animation. When the spinner is deleted (response posted), the embed goes with it. A final standalone post at teardown leaves a permanent record below the response. `setSpinnerEmbed` was added to `bot-spinner.ts`; `stream-processor.ts` replaces mid-session syncs with `pushEmbedToSpinner` and adds a single `syncDiscordTodoEmbed` at teardown. The teardown post was restored with handling for deleted-task status after a regression (`f09b06efb5`).

**Lesson Learned:** Task visibility compounds. A live embed is useful. A live embed that travels with the spinner is better. Each layer is cheap to add once the prior one exists — but the layers have to be wired to the right async path from the start.

### Memory Injection: Thread-Linked Embeds

**Commit `c7c0e916f7`**

The memory hook's output is now attached to Discord embeds with bidirectional thread linking. Memories surface in chat with full context and two-way navigation — from the memory to the thread where it was created, and from the thread back to the memory.

**Lesson Learned:** Memory that surfaces without context is a reference; memory that surfaces with thread linkage is a trail. The difference is whether you can follow the chain back to where the memory was formed.

## Reflection: Week 42

---

### The Mistakes We Made

#### 1. Todo Embed Posted to Wrong Async Path

**Cost:** The live todo embed was initially placed in `stream-processor.ts` — the web/API execution path — rather than `spawn-sync.ts`, the Discord spawn path. The feature appeared to work in isolation but missed the actual Discord session execution path.\
**Fix:** `479dff6ba5` and `2545c0a7f2` — moved to the correct path.\
**Lesson Learned:** Discord-spawned sessions have a different execution path than web sessions. Features targeting Discord behavior belong in `spawn-sync.ts`, not `stream-processor.ts`. The two paths look similar and serve the same upstream callers, which makes the mismatch easy to miss until the feature lands in production.

#### 2. TikTok Archive Ingest Without Sufficient Dedup Guard

**Cost:** Multiple bulk TikTok archive batch imports were reverted on August 8 and 9 (`4307c005`, `3416727159`) — the ingest created duplicates that required cleanup and re-processing.\
**Fix:** Revised the ingestion flow to enforce dedup before writing.\
**Lesson Learned:** Bulk historical imports need a stronger dedup gate than real-time bookmark processing. Volume amplifies any gap in dedup logic — what fails silently at 1 record per run fails visibly at 100.

#### 3. herdr systemd Unit Type Wrong

**Cost:** `Type=forking` caused systemd to wait for a child process that herdr never forks — the unit appeared to start but timed out waiting for a PID it would never receive.\
**Fix:** `20ce490390` — changed to `Type=simple`.\
**Lesson Learned:** systemd unit types aren't interchangeable. `Type=forking` is for daemons that deliberately double-fork and write a pidfile; services that stay in the foreground should always be `Type=simple`. Getting this wrong during a migration is easy because the unit "appears" to start before timing out.

### The Surprising Things

#### 1. The Mac Mini Was Already the Right Proxy

**Expected:** Solving the Hetzner TikTok geo-block would require a new infrastructure component — a VPN, a proxy service, or a dedicated download host.\
**Actual:** The Mac mini at `100.78.238.106` was already handling voice memo pre-staging over Tailscale. Adding TikTok as another task on the same proxy required no new infrastructure — just a new path through an existing pattern.

The voice-memo-watcher architecture (stage on Mac Mini, scp back, process on Hetzner) turned out to be a general pattern for bypassing geo-restrictions for any media type.

#### 2. Five-Database PITR Was Mostly Parameter Substitution

**Expected:** Extending PITR from `andy_core` to all five databases would require significant rearchitecting — new backup scripts, new monitoring, new retention logic.\
**Actual:** The Week 41 backup architecture was already parameterized correctly. Extending to 5 databases was primarily updating path templates and adding a connectivity note for `markdawn`'s pasta networking. The heavy architectural work was done once; scaling it was mechanical — 500+ lines of changes that were mostly variable substitution and loop additions.
