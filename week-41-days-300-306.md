## Days 304-305: The JFDI Recorder Sprint (August 1–2, 2026)

### Overview

August 1 opened with a blank `/record` route. By August 2 at midnight it was a functioning browser recorder. By August 2 end of day it was a production PWA with four reliability layers, Plyr-powered audio playback, inline transcript previews, iOS-specific interrupt handling, and a Replay button linking to published meeting pages. The PostgreSQL backup system reached the same milestone in parallel: WAL streaming to DO Spaces, GFS tiered retention, `pg_archivecleanup` pruning, and a successful restore test all landed the same two days.

### Phase 1: Browser Recorder from Zero to /record

**Commits `6ae03755b70d` (Phase 1), `ec479964142d` (Phase 2), `7067c1b5ab8c` + `85213678a53b` (Phase 3)**

August 1 afternoon built the recorder in three phases:

- **Phase 1** — presign endpoint at `POST /api/record/presign` for direct-to-Spaces upload; client gets a signed URL and POSTs the Blob directly, bypassing the server for the file transfer
- **Phase 2** — watcher integration: the existing meeting-replay watcher watches the recording's DO Spaces path and triggers transcription + publishing the same way it handles voice memos
- **Phase 3** — production recorder page at `/record.html` (later `/record`): React + shadcn UI, session auth wired, recent recordings list pulled as Inertia props, recordings capped to show below the fold

The architecture used the entire meeting-replay pipeline unchanged — same transcription, same watcher, same publishing. The recorder is an input to infrastructure that already existed.

**Lesson Learned:** When infrastructure already exists, the new feature is just a new input path. The recorder didn't need a new pipeline — it needed a presign endpoint and a React page to feed the one that was already there.

### PWA: Icons, Manifest, and Safe-Area Polish

**Commits `92c66a83c5d0`, `760379f97c66`, `63124f4f8b06`**

The recorder route got its own `record.webmanifest` with `start_url: /record` so home screen shortcuts open the recorder, not `/chat`. A JFDI-style mic icon replaced the generic record-circle icon at 180/192/512px. Safe-area-inset-top padding was added for PWA standalone mode to prevent the Dynamic Island from bleeding into the header.

**Lesson Learned:** PWA route isolation matters. A shared manifest that points to `/chat` makes the recorder shortcut a disappointment on every launch. One extra manifest file, one better experience.

### Voice-Memo-Watcher Hardened Against tmpfs Cascade

**Commits `4d37f98b7677` (fix), `b57c96aa2fd0` (architecture fix)**

A cascade bug in the voice-memo-watcher was fixed the same day as the recorder build — related territory, same instinct toward reliability. The bug engine: a failing memo looked "new" on every cycle, wrote a 32MB partial to `/tmp` each time, and fired a Discord ping per cycle. Five fixes addressed it:

- `res.on('error')` on the HTTP stream to catch `ECONNRESET` mid-transfer
- `try/finally` in `uploadAudioEarly` so temp files are always cleaned up
- Backoff-aware filter respecting `download_failed` + `nextRetryAt` state
- Exponential backoff on failure (1m→5m→15m→60m), persisted across cycles
- Stale-sweep of `/tmp` partials older than 1 hour as self-healing backstop

The architecture fix replaced HTTP streaming entirely with `stage + rsync`: a `/voice-memo/stage` endpoint copies the file to a staging directory inside the TCC-privileged server process, then rsync pulls it resume-capable and checksum-verified. Two integrity layers, graceful network-drop recovery.

**Lesson Learned:** A cascade needs only one unhandled failure path to spin up. The tmpfs cascade had five contributing factors — fixing one would have reduced it, but all five needed addressing to close the class of failure.

### 4-Layer Recording Reliability Architecture

**Commits `6de20e750a16` (Layer 1: IndexedDB), `6313d1dc8fb6` (Layer 2: chunked server upload), `3af6022ad98f` (iOS interruption), `dc127dfe431b` (debug panel)**

August 2 added the reliability layers that make the recorder trustworthy for real sessions — not just demos:

**Layer 1 — IndexedDB local backup (`6de20e750a16`):** Every 1-second MediaRecorder chunk is written to IndexedDB immediately under the recording's filename key. On successful upload the entry is cleared. On page load, orphaned recordings surface as a recovery UI — upload or discard each one. This layer is entirely client-side and fires before any network call.

**Layer 2 — Chunked server upload with auto-heal (`6313d1dc8fb6`):** Every 60 seconds during recording, accumulated chunks POST to `/api/record/chunk`. The server writes each batch atomically (`.tmp → rename`). On Stop, `/api/record/complete` triggers server-side assembly and direct S3 `putObject`. Resilience properties: idempotent chunk endpoint (safe to retry), exponential backoff (3 attempts, 2s/4s/6s), `pendingChunks` Set ensuring complete fires only after all ACKs, server-side fallback to IDB + direct PUT on assembly failure. Short recordings under 60 seconds skip the server path entirely.

**iOS AudioContext interruption (`3af6022ad98f`):** `AudioContext.statechange` doesn't reliably fire when Control Center interrupts the mic on iOS. `MediaStreamTrack mute/unmute` events are the correct signal. Five-second chunk gaps with no suspended log in the debug panel confirmed this empirically.

**Debug panel (`dc127dfe431b`):** A rolling on-device debug panel (toggle via "dbg" in header) logs IDB chunk writes, upload phases, presign results, MediaRecorder state changes, and AudioContext transitions — visible on the device without DevTools.

**Lesson Learned:** Four reliability layers sounds like over-engineering until a network drop or iOS interrupt silently discards a 45-minute session. The layers are cheap; lost recordings are not.

### JFDI Recorder Polish: Blob Visualizer, Plyr, Cards, and Finishing Touches

**Commits `9761de35a374`, `5d94156e0fc2`, `9594801e29b8`, `b3a4113214798`, `2756a57167c1`, `1a7a3dd0f8cd`, `d446230557af`, `d7b913b10b51`, `61241f20d2ab`**

August 2 turned the functional recorder into a finished product:

- **Breathing blob visualizer** — the bar chart was replaced with an amber breathing blob that responds to microphone input. Idle state gets a blue-500 sine-wave animation so the canvas is never blank.
- **Cancel confirm** — a two-line "are you sure? / tap again" label appears on first cancel tap; second tap discards. No accidental recording loss.
- **Plyr audio player** — native `<audio>` replaced with Plyr, styled to match app design tokens (primary yellow, card bg, border, radius via CSS variable overrides). FloatPlayer PIP inherited from meeting replay.
- **Status filter dropdown** — a right-aligned dropdown on the RECENT section filters by status (All / Ready / Transcribing / Processing / Done / Skipped / Failed).
- **Tap-to-expand cards** — cards toggle inline to show the audio player and transcript preview. ChevronDown rotates on expand. Controller passes `title`, `mediaUrl`, and `transcript` from `meeting-replay-state.json`.
- **Replay button** — when a published replay page exists in `catalog.json`, the status badge is replaced with a primary "Replay →" button opening the page in a new tab.
- **Local time on cards** — `meetingTime` (UTC) combined with `meetingDate` and rendered via `toLocaleTimeString()` so timestamps reflect the client's timezone.
- **Light/dark toggle** and **renamed header** — header renamed to "JFDI Recorder"; light/dark mode toggle added.

**Lesson Learned:** The reliability layers made the recorder trustworthy. The polish layer made it worth using daily. Both are necessary — a reliable ugly tool gets abandoned; a beautiful unreliable one gets distrusted.

### PostgreSQL Backup Reaches Production Confidence

**Commits `2417877d353f` (WAL offsite), `8980df4710f4` (pg_archivecleanup), `cb4ac1a47a9f` (tiered GFS), `f948c7a22de4` (retention tightening), `87221e3667d1` (Spaces WAL prune), `1c53a97c6dbf` (restore test + hourly pg_dump), `e3a7e8050cfb` (restore runbook)**

The backup system completed its reliability arc across the same two days:

- **WAL streaming to DO Spaces** (`2417877d35`): `sync-wal-to-spaces.cjs` syncs `/backups/wal/` every 10 minutes, excluding in-progress `.partial` segments. Nightly `pg_basebackup` now syncs to Spaces under `backups/pg-basebackup/YYYY-MM-DD/`, verifies `backup_label` exists before pruning any local copy. Local pruning is gated on Spaces verification — no local delete without a confirmed remote copy.
- **WAL pruning** (`8980df4710`): `pg_archivecleanup` prunes WAL segments older than the oldest retained base backup after each nightly run. Guard: cut-point segment must exist in DO Spaces before any local WAL is deleted.
- **Tiered GFS retention** (`cb4ac1a47a`): 4 hot copies / hourly for 12 hours / daily, matching a Grandfather-Father-Son retention model.
- **Spaces WAL prune** (`87221e3667`): A `.wal-start` sidecar file (~24 bytes) uploaded after each base backup carries the backup's WAL start segment. Spaces WAL pruning reads this sidecar — no need to download the full tarball to find the cut point. Paginated S3 listing handles the volume (WAL exceeds 1,000 objects).
- **Restore test** (`1c53a97c6d`): 145,000 sessions + 1,120 reminders recovered clean from base backup + WAL replay. Documented gotchas: `podman unshare chown` for rootless Podman, edit-before-chown order, stage on main disk not `/tmp` (base backup is ~8GB), `pg_stat_user_tables` shows zeros on fresh restore (use `COUNT(*)`). Closes #445 and #496.
- **Restore runbook** (`e3a7e8050c`): Full step-by-step documentation of both local and DO Spaces restore paths. Closes #496.

**Lesson Learned:** A backup system you've never restored from is a hypothesis, not a guarantee. The restore test on August 2 converted the backup system from "probably works" to "demonstrated to work." The runbook is what lets you repeat it under pressure.

## Day 306: herdr 0.7.5 Mapping, the 78-Day Silent Alarm, and env Scrub (August 3, 2026)

### herdr 0.7.5 Compat: Fix Landed and Reverted

**Commits `9c0d7056ca72` (env scrub), `5e0bd69f5770` (compat fix), `f7ae46d8308b` (revert)**

The herdr 0.7.5 upgrade removes `agent send` — a command the Discord bridge's blocked-choice handler relies on. A fix landed (`5e0bd69f57`): the handler now calls `agent prompt`, which atomically submits text + Enter in a single command, eliminating the previous two-call pattern (send choice, then send `\r`). 

The fix was reverted the same session (`f7ae46d830`). Reason: the companion invoker changes live in the `herdr-075-compat` branch in jfdi. Both sides must deploy together; shipping the bridge side alone would break the current binary.

Separately, `9c0d7056ca` fixed a subtler herdr bug: when herdr >= 0.7.5 launches pane agents directly (no `bash -c` wrapper), pane shells inherit the server's environment verbatim. A server restarted from inside a Claude Code session carries `CLAUDE_CODE_*` and `ANTHROPIC_BASE_URL`, making pane claudes detect a nested session — transcript saving turns off, jfdi hangs waiting for a transcript that never comes, API calls route through the caller's proxy. The PM2 wrapper now unsets all `CLAUDE*`, `ANTHROPIC_*`, and `AI_AGENT` variables before exec'ing the herdr-real binary.

**Lesson Learned:** The fix-and-revert pattern isn't a mistake — it's correct sequencing. Landing half of a bundled change breaks the current system. The branch exists; the coordination cost is explicit; the revert preserves the current working state.

### Watchdog Finds a 78-Day Silent PM2 Daemon

**Commit `e7ad9e6735c9`**

The PM2 God Daemon (PID 3222908) had been stuck in D-state for 78 days. The watchdog had logged it as an ongoing issue after the initial alert — but ongoing issues were never re-alerted. The /tmp state file persists across runs on a VPS that hadn't rebooted in 78 days, so the daemon stayed in "ongoing" state and was seen every 15 minutes for 78 days without generating a single notification.

The fix adds `firstSeen`/`lastAlertAt` tracking to watchdog state and re-alerts high-severity ongoing issues every two hours. The re-alert includes the same triage and dismiss checks as a new-issue flow. An explicit PM2 God Daemon check via `.pm2/pm2.pid` was also added — `pm2 jlist` hangs if the daemon itself is stuck, so the check bypasses it entirely.

**Lesson Learned:** "Seen before" is not the same as "resolved." An issue that fired once and was never re-alerted effectively silences itself. Ongoing severity thresholds need periodic re-alerting, not just first-detection firing.

## Reflection: Week 41

---

### The Mistakes We Made

#### 1. herdr 0.7.5 Bridge Fix Shipped Without Its Companion

**Cost:** The discord-agent-bridge compat fix for herdr 0.7.5 landed without the jfdi invoker companion changes, which live in a separate branch. Shipping half a bundled change would have broken the current working binary.\
**Fix:** `f7ae46d830` — reverted immediately; both sides must deploy together.\
**Lesson Learned:** Bundled deployments require explicit coordination gates. A fix in isolation is not a fix if it depends on a companion change that isn't live.

#### 2. Watchdog Silenced Itself for 78 Days

**Cost:** The PM2 God Daemon had been in D-state for 78 days with no re-alerts — a silent infrastructure problem invisible to the monitoring system because "ongoing" issues were only alerted once.\
**Fix:** `e7ad9e6735` — added `firstSeen`/`lastAlertAt` tracking and a 2-hour re-alert cadence for ongoing high-severity issues.\
**Lesson Learned:** Monitoring that fires once and goes quiet is indistinguishable from no monitoring after the first notification. Ongoing severity requires ongoing alerts.

#### 3. AudioContext.statechange Doesn't Reliably Fire on iOS

**Cost:** The first iOS interrupt handler for the recorder used `AudioContext.statechange`. Under a real Control Center interruption, it didn't fire — confirmed by a 5-second chunk gap with no "suspended" log in the debug panel.\
**Fix:** `3af6022ad9` — replaced with `MediaStreamTrack mute/unmute`, the correct iOS signal for audio interruptions.\
**Lesson Learned:** Web audio APIs have platform-specific behavior that documentation doesn't predict. The debug panel paid for itself in the first real test: the gap in the log identified the broken signal immediately.

---

### The Surprising Things

#### 1. The Entire Meeting-Replay Pipeline Was Already the Right Architecture

**Expected:** Building a browser recorder would require a new transcription + publishing pipeline.\
**Actual:** The watcher, transcription job, and replay publishing system required zero changes. The recorder needed only a presign endpoint and a React page — everything downstream was already in place.

The recorder was an input path to infrastructure that already existed. The fact that Week 37's meeting-replay build was architected as a general pipeline rather than a voice-memo-specific one meant a new recording surface required almost no backend work.

#### 2. A Backup System Can Pass Its Restore Test and Surface New Gotchas

**Expected:** A restore test is a pass/fail verification.\
**Actual:** The August 2 restore test passed AND generated five documented gotchas (rootless Podman `unshare chown` order, staging directory location, `pg_stat_user_tables` zero-on-restore false negative, replication slot removal). Passing isn't the same as learning nothing. The runbook exists because of what was discovered during a successful restore.
